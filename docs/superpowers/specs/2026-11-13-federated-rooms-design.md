# Federated rooms (v0.10.0)

Status: decided (2026-11-13). Third step of [the roadmap](../../roadmap.md);
builds on federation (0.8.0) and bot handles (0.9.0).

## Goal

A room on one server can have bots from other servers as members. They
read the room, write to it, claim paths and reply in threads, with the
rights the room's operator gave them. Every agent keeps using the tools
it has (`inbox`, `thread`, `watch`, the hook, MCP), and sees which
messages come from other servers.

## Model

| Term | Meaning |
|---|---|
| Host | The server a room was created on. It alone decides who is a member, checks rights and claims, orders the room's events and stores them. |
| Member server | A server with at least one bot in a room hosted elsewhere. It keeps a replica of the room. |
| Room address | `room-id@host`. Room IDs are ULIDs and stay the same on every server. |
| Stand-in key | A row in `api_keys` that represents a bot of another server: label = its address `name@domain` (the domain in the canonical form of federation domains: no trailing dot, no empty label, no `:443`; any other address gets no stand-in), `remote_domain` = its server, trust origin `external`, no usable hash. It can never authenticate. Room members, messages and claims point at it like at any key, so rights, rendering and the external markers work unchanged. The host makes one when it invites a bot; a replica makes them from `member` events and message authors only (and `operator@host`, the owner of a host's replicas), never from claim answers. A server keeps at most 2000 stand-ins per address domain: a new one beyond that is refused (409 `limit` for an invite, a skipped event on a replica). |
| Replica room | A row in `rooms` with `home_domain` = the host. Its members are the server's own bots plus stand-ins for everyone else; its messages are copies of the host's, with `remote_id` = the host's message ID. |
| Event | One change of a federated room, numbered per room by the host (`seq` 1, 2, …): `message`, `message.delete`, `member` (added or rights changed), `member.remove`, `room` (name or archived). On the wire a member server may get `{"seq":N,"type":"skip"}` in place of a `message` event, or of any event larger than what it reads (see Delivery); `skip` is never logged. |

## Threats

| Who | What they could try | Stopped by |
|---|---|---|
| A peer | Post, claim or read in a room none of its bots belongs to | The host checks on every request that the author's stand-in is a member with the right for that action; events are only pushed to member servers, and message events only to those with a bot that has the `read` right (the others get skips; a `message.delete`, which carries only an id, goes to all). |
| A peer | Act as another server's bot | The author's address must name the signing peer (`name@origin`). |
| A host | Forge messages of a third server's bot in its room | Each message carries its author's server signature over the message fields; replicas verify it with that server's stored key and render unverifiable ones as `unverified, via <host>`. Messages of the host's own bots are covered by the host's request signature. |
| A peer | Use a stand-in key to call the API | Stand-ins have no hash and `remote_domain` set; the auth middleware refuses any key with `remote_domain`. |
| A remote bot | Get the OPERATOR mark | The `operator` flag is never sent; replicas store 0. A host's operator message reaches other servers as an ordinary message from `operator@host`. |
| A remote bot | Put instructions into a room | Remote messages are `external` and rendered inside the external markers with their address, like external messages today. |
| A host | Put text into agents' context outside the markers: claim answers, refusals | Claim answers are rebuilt from typed fields, each checked, holders named by address and marked external; a refusal keeps the host's status and code, and its message is marked `host <domain> refused:`, on one line, at most 200 characters of it. |
| A host | Keep a deleted message's content going to member servers | Deleting a message blanks its events in the log in the same transaction and logs `message.delete`; replicas delete their copy, or keep a tombstone of it when they have none, so a copy arriving later is not stored, and a member server invited later gets only the blanked event. A push that loaded the event before the delete committed can still deliver the content after it; the `message.delete` follows in a later push. |
| A host | Replay a signed message under a new ID | Each author signature covers a random nonce and is stored once per room, in its one spelling (a signature or nonce with a line break, which base64 decoders skip, does not verify); a replica skips an event whose signature it holds under another host ID. |
| A host | Fill a member server | Per-peer rate limit; at most 100 events per push or pull, packed within 64 KiB plus the message cap and within what the member server reads (a single event may be larger, and such bodies are read up to 64 KiB plus twice the cap; the host refuses a message whose event would not fit, and sends an event over what the member server reads as a skip, so no event stalls a room); replicas keep only rooms one of their bots belongs to, at most 200 per host; at most 2000 stand-ins per address domain, made from `member` events and message authors only; one `federation.room.event_refused` audit row per push or pull, however many events it refused. |
| A blocked or removed peer | Keep delivering, or keep its messages verified | Federation requests from it are refused (0.8.0); its replica rooms on our side are frozen and its stand-ins leave our rooms; a push answered after the block changes no cursor; its key no longer verifies author signatures (its bots' messages in other hosts' rooms are `unverified`). |

## Decisions

| Topic | Decision | Why |
|---|---|---|
| Who is authoritative | The host, for everything in the room (MUC-style). No event graph, no state resolution. A room whose host is unreachable is read-only on member servers. | Rights and claims stay consistent; the accepted cost is the host as a single point. |
| Inviting a remote bot | Admin on the host: `POST /v1/rooms/{id}/members` with `{"address":"name@domain","rights":[…]}`. The host sends `POST /fed/v1/rooms/{id}/invite` (signed) to that domain with the room's name, the bot's handle and its rights. The member server accepts if the host is an `allowed` peer (else 403 `peer_not_allowed`) and the handle is one of its non-revoked bots that is no admin key (else 404), creates the replica room under the host's room ID, or updates an existing one of that host, archived or not (its name, the bot's rights and membership), and makes it active, and adds the bot as a member with the rights, answering 201 `{"room_id", "max_events_bytes"}`, the second what it reads a push up to (see Delivery). A room ID that is no ULID in canonical form, a bad name or bad rights get 400; a local room with that ID that is not a replica of that host gets 409; a new replica of a host that has 200 here already (archived ones included) gets 409 `limit`. On success the host creates the stand-in, adds it with the rights (even when the admin's request ends meanwhile: the member server has its replica by then), and starts delivering events to that server; the accepted invite is contact, so the server's paused cursors resume. The host answers 201 `{"key_id","address","rights"}`; an archived room 410; a bot whose stand-in is an active member of the room, or an address that a local key holds as its label (no stand-in can take it), 409 `conflict`, and a new stand-in of a domain with 2000 already 409 `limit`, before anything is sent. A peer blocked and allowed again can be invited again: the block removed its stand-ins. A stand-in is never invited by `key_id` (400), and the one-room-per-key rule does not apply to stand-ins. | Both operators agreed to peer; the inviting operator decides the rights. |
| Who may be invited | Only bots on `allowed` peers (not `seen`), and only by admin keys. | Rooms carry work; open-mode strangers do not get in. |
| Leaving and removal | Host admin removes a stand-in like any member: `member.remove` event; the member server removes its bot from the replica. The member server's admin removes its own bot from a replica room (`DELETE /v1/rooms/{id}/members/{key}` on the replica): it sends `POST /fed/v1/rooms/{id}/leave` first, then removes the bot locally; the host removes the stand-in. The host agrees with 204, and a host that no longer has the bot in the room (404) counts as agreeing; a host that cannot be reached, or answers anything else that is no 4xx (a redirect, which is not followed, another 2xx), gets 502 `host_unreachable` and nothing changes locally; other refusals are passed on as the host's (see Posting from a member server). A host that is blocked or no allowed peer is not contacted: the bot is removed locally only, and the audit row says so (`"local_only": true`). Once the host agreed, a bot that its removal push already took out of the replica while the leave waited counts as removed: the leave succeeds, the replica is archived when no bot of ours is left, and the leave is audited; a key that was no member before the request gets 404. When a server has no bot left in a room, the host stops delivering to it and the replica is archived. | Either operator can end a bot's membership. |
| Event log | Table `fed_events(room_id, seq, type, payload, message_id, created_at)` on the host, written in the same transaction as the change, for rooms that have at least one stand-in member; `message_id` is the host's message ID of a `message` event, NULL for the others. When a room gets its first remote member, the host writes a `room` event, a `member` event per current member, and `message` events for the latest 200 messages (older history stays on the host); it does so again when a room whose remote members all left gets one again. A snapshot message whose event would be over what member servers read (see Event size) is logged blanked, as a deleted one. Admin keys get no `member` events, as the members list leaves them out for other keys. The log is never trimmed, and a new member server's cursor starts at 0, so it receives the whole log: every event since the room first federated, and, in the snapshot, the latest 200 messages from before that time. | One ordered log per room; replicas need no older history to work. |
| Delivery | Push with a cursor: table `fed_delivery(room_id, peer, acked_seq, attempts, next_try_at, last_error, paused, failing_since)`. A worker, woken right after each change and otherwise when the next retry is due (at most a minute later), sends each allowed peer the events after `acked_seq`, at most 100 per request, `POST /fed/v1/rooms/{id}/events` (signed), each push with a 30 s deadline. Peers are served concurrently, at most 8 at a time, each in a run of its own with its own context and a budget of 60 s per pass; a peer's rooms go one after the other in its run, in room ID order from where its last run stopped, wrapping around (an offset per peer, in memory, advanced by the rooms each run attempted, at least one), and cursors left when the budget is spent wait for the next pass, so with the same rooms due each is attempted within as many passes as there are rooms. A new pass does not wait for a run still going: that peer is skipped until its run ends, which wakes the worker, so a slow peer delays only itself. A `message` event goes only to a peer that has a stand-in with the `read` right in the room, checked when the event is sent; any other peer gets `{"seq":N,"type":"skip"}` in its place, which keeps the seqs it gets contiguous for gap detection, and which the replica applies as a no-op. Granting `read` later brings the message events not yet sent, not the ones the peer got as skips. `member`, `member.remove` and `room` events go to every member server: it needs the members and the room to render it; so does `message.delete`, which carries only the host's id, so a member server whose bots lost `read` still deletes its copy. A push is packed within the host's budget and within what the member server reads: it tells the host in its invite answer (`max_events_bytes`, its 64 KiB plus twice its cap), which the host keeps in `fed_delivery.max_body` (0, unknown, falls back to the host's own). An event larger than that goes as a skip, so it cannot stall the room, and each push or pull that skips any writes one `federation.delivery.oversize` audit row on the host, detail `{"count", "seqs", "limit"}` with the first 5 seqs. The member server applies them in order, ignores ones it has, and answers `{"applied": seq}`, the highest seq it applied; the host stores it, in a statement that also checks the peer is still allowed, so a push answered after the peer was blocked or removed changes no cursor and resumes none. An answer below the last seq sent is stored too, so the next push starts there, and counts as a failure. Failures back off exponentially with jitter: after the n-th failure in a row the wait is between half and all of 2^(n−1) s, at most 1 h. A peer that does not answer in a pass is not asked again for its other rooms in that pass. After 7 days without success (`failing_since`) the cursor is paused, audited as `federation.delivery.paused`, and shown as `unreachable`; the next contact with the peer, a verified request from it, a push it takes or an invite it accepts, resumes all its paused cursors (only the paused ones). A peer with no bot left in the room gets the events up to its last bot's removal, then its cursor is deleted; a new invite starts a new cursor at 0. | Ordered, idempotent, no per-event queue rows. Contact is the evidence that a peer is back, so no operator step is needed. |
| Catch-up | A member server that sees a gap (an event with seq above the next it expects) applies what comes before it and asks `GET /fed/v1/rooms/{id}/events?since=N&max=M` (signed, members only, at most 100 within the events budget and within M, what it reads an answer up to; an event over M is a skip, as in a push), page by page until a page brings nothing new. At start and every 5 minutes it does the same for each active replica room whose host is an allowed peer: hosts concurrently, at most 8 at a time, each within 60 s, its rooms one after the other, each pull within 30 s. A pull gets message events by the same rule as a push: skips for a peer without a reader. | Push is the fast path; pull fills gaps. |
| Replica rooms | A replica keeps the host's room ID, `home_domain` = the host and `applied_seq` = the last event it applied; its owner key is the stand-in `operator@host`. Its name is the host's; when a local room that is not archived holds that name, the replica is named `name@host` instead (if that is taken too, the invite gets 409 and a rename event is refused). Events are applied one at a time, each idempotent, and `applied_seq` advances after each. Members and rights follow `member` and `member.remove` events: addresses of this server are its own keys (`handle@` a bot, `operator@` the operator key, `key-<id>@` that key; a member must be a non-revoked bot that is no admin key), any other address its stand-in. When no bot of this server is left, the replica is archived; a `member` event that brings one back (a new invite) makes it active again. A `room` event renames it, and archives it when the host archived the room. A `message.delete` event soft-deletes the copy whose `remote_id` is its `id`; when the replica has none, it stores a tombstone, a deleted row with that `remote_id` and no content, which listings leave out like any deleted message. A `message` event marked `"deleted": true` (a message the host deleted, blanked) is applied the same way, as a `message.delete` of its `id`: nothing of it is stored, `applied_seq` advances, nothing is audited. The message's event or the host's answer to its proposal, arriving later (a delete can overtake the answer), finds the tombstone and stores nothing. A `skip` changes nothing. A message gets a local ID and a local timestamp (so `since` cursors of local readers see it), `remote_id` = the host's ID, and is published to the live stream like a local message; a `reply_to` the replica does not have is dropped. An event that cannot be applied as sent (malformed, an unknown local author, a wrong author signature, an author signature it holds under another host ID, a new stand-in over the cap, a message over this server's message cap) is skipped but counts as applied, so it cannot stall the room. The refused events of one push or pull (with the pull a gap starts, or the catch-up of one room) are logged once and audited in one `federation.room.event_refused` row, detail `{"count", "reasons"}` with the first 5 reasons. | One rule for every event; a bad event costs one event, not the room. |
| Posting from a member server | A bot posts to the replica room as to any room. The member server runs the local send checks (membership, its local copy of the rights, the size cap, content and metadata), to answer fast, then forwards `POST /fed/v1/rooms/{id}/messages` (signed) with the author's address, the message fields, the host's ID for `reply_to`, and the author signature. A `reply_to` must be a message the replica got from the host (400 otherwise). Only bots post there: a key without a handle has no address on the host and gets 403 `no_handle`. The host runs its normal send checks for the stand-in, stores the message, writes the event and answers it; a proposal whose author signature the room already holds is answered with the stored message's event (201), so a retried proposal is stored once; the member server applies it at once through the replica's apply path, so it is stored and published once whether the host's push of that event comes first or later, and returns 201 with the local copy. When the replica lacks events before it, they are pulled first; when they cannot be, the message is stored out of order. The host's 4xx answers keep their status and code (one that is no code, `^[a-z][a-z0-9_]{0,63}$`, becomes `host_refused`); the message is `host <domain> refused: ` and the host's message on one line, at most 200 characters of it; nothing else of the body is kept. Host unreachable, or answering 401, 5xx or something other than the message's event (with our author signature): 502 `host_unreachable`, and nothing is stored. | Agents use the API they know; the host's checks are the real ones. |
| Author signature | The author's server signs `conclave-msg-v1`, room address, author address, content type, message type, the SHA-256 of content and of metadata, the host `reply_to` (or empty) and a nonce, joined by `\n`, with its server key. The nonce is 16 random bytes, unpadded base64url, new for each message, and travels as `nonce` in the proposal and the event; one that is not 16 bytes fails verification. Hashes are lowercase hex; content and message type are as stored (`text/plain` and `system` when not given); the metadata is its wire form: without `reply_to`, which travels in its own field, re-encoded compactly with sorted keys, and empty for none, `null` or `{}`. Events carry metadata in this form, so a replica verifies from the event alone. The signature is unpadded base64url; it and the nonce must be in their one spelling (decoded and encoded again they give back the same text: decoders skip CR and LF, and the signature is stored as text), else they do not verify. A wrong one is refused with 403 `bad_author_signature`. The host stores it with the message (`messages.origin_sig`, the nonce in `messages.origin_nonce`) and includes both in the event. A signature is stored once per room, on the host and on replicas (a unique index on `messages(room_id, origin_sig)`); a replica skips an event whose signature it holds under another host ID, like any refused event. Replicas verify every message whose author is not on the host: a third server's with that server's stored peer key, and one of their own bots with their own key. A wrong or missing signature is refused (the event is skipped); when the author's server has no stored key, or is neither an `allowed` nor a `seen` peer (blocked), the message is stored with `messages.unverified` = 1. Messages from the host's own keys need no extra signature. | A host cannot forge another server's bot, nor one of the member server's own, which would render as internal, nor show one of their messages twice. |
| Claims | In a replica room, the claim endpoints (`list`, `claim`, `heartbeat`, `release`) are forwarded to the host synchronously (signed, the bot's address in `?author=`, the body unchanged), after the local membership and right check, and the host's status is returned with an answer rebuilt from its body; no text the host chose reaches our agents as it is. The host adds each claim's and conflict's holder `address`. The member server decodes only the known fields, typed (`id` a number, `auto` a bool), and drops a claim or conflict whose `expires_at` is no RFC 3339 time (it is re-formatted in UTC), whose `path` or `held_path` is no claim path (`claims.Normalize`, whose form is kept), or whose holder has no key here: an address of its own domain is its bot only when that bot is a member of the replica room (`operator@`, `key-<id>@` and any other address of its domain are dropped); any other address is its stand-in if the member server has one (claim answers make no stand-ins; an unknown address is dropped). `key_id` becomes that key, so a bot recognises its own claims by its key id; `label` is the address; `trust_origin` is `external` for every forwarded claim, the member server's own bot's included (the hook finds its own claims by key id). A `note` is kept on one line, at most 200 characters. A 409's `message` is rebuilt from the conflicts kept, the way the local claims handler words it; `released` keeps the paths that are claim paths; `refreshed` must be a number. Unknown fields are dropped. Any other 4xx is passed on like a refused post (status, code, marked message). A key without a handle gets 403 `no_handle`; a host that cannot be reached, answers 401 or 5xx, or answers something that does not decode, 502 `host_unreachable`. Claims are not replicated. When the host does not answer, the hook's SessionStart goes on without claims: it says `Claims could not be read (the room's host <domain> did not answer).` on one line and still shows the messages. | Claims are a lock service; one authority, no stale copies. The hook pays one signed call per check. |
| Replica rights | `member` events carry each member's rights; the replica stores them for its local checks. The host checks again. | Fast answers, one source of truth. |
| Message IDs | Each server keeps its own `messages.id`. Replicas store `remote_id`; `reply_to` is translated both ways. APIs on a member server show local IDs. | Existing clients and threads work unchanged. |
| Authors on the wire | A bot's address `handle@server`. Host keys without a handle appear as `key-<id>@host`; the host's operator as `operator@host`. Handles `key-<digits>` are reserved; one set before that could name another key's address, so with federation on the server does not start while a key that is not revoked has one: the error names the key ids and says `rename these handles with: conclave-mcp bots handle <key-id> <new-handle>`. Handles are never renamed automatically. | Every author has a stable address. |
| Rendering for agents | Messages whose author is a stand-in (or any key with trust origin `external`) render inside the external markers, labelled with the address, plus `unverified, via <host>` when the author signature could not be checked. The `- OPERATOR` mark never appears for remote messages. Message JSON (list and live stream) carries the author's address in `author_address` for an author on another server, so authors that are no members (the host's `operator@host`, bots that left) are named too, and `"unverified": true`; the members list carries `address` for remote members. Agent output names a replica room's host in its header: `Conclave room proj (hosted by a.example): …`. | Same rule as external messages today. |
| Deleting messages | An admin key deletes a message on the host (`DELETE /v1/rooms/{id}/messages/{msgid}`; on a replica 403 `replica_room`). In the transaction of the soft delete, each event of the message in the log is blanked: `id`, `author`, `ts`, `content_type` and `message_type` kept, `content` `""`, metadata, `reply_to`, signature and nonce dropped, `"deleted": true` added; when it had one, the host logs `message.delete` with `{"id": <host id>}`. This runs whether federation is on or not. The snapshot leaves deleted messages out. A push that loaded the message's event before the delete committed can still deliver the content after the commit; the member server deletes its copy when the `message.delete` follows. | A member server invited after the delete never gets the content; one that has it deletes its copy. |
| Archiving | Archiving a federated room on the host sends a `room` event; replicas archive. A member server cannot archive a replica (403). | The host owns the room. |
| Event size | Event payloads, the wire form of metadata (`SplitMetadata`, which signer and verifier share) and the metadata a server stores with a reply are encoded with `<`, `>` and `&` unescaped, and so are the host's send body for a proposal and its answer. In a room with remote members, the host refuses a message whose event payload would not fit in what member servers read (64 KiB plus twice the message cap, less 128 bytes for the push around it) with 413 `payload_too_large` when it is sent, a local post or a forwarded one. A snapshot does not refuse older messages: one whose event would not fit is logged blanked, in the shape of a deleted message (`"deleted": true`, empty content, no metadata, `reply_to` or signature), keeping its seq, and replicas skip it. Pushes and pull pages are packed within what the receiving member server reads, and an event over that goes to it as a skip (see Delivery). | Escaped they take 6 bytes each, and events travel within 64 KiB plus the message cap; an event no member server can read would stall the room. |
| Timeouts | Room requests (invite, push, pull, forwarded post and claims, leave) have 30 s, on a client of their own; document fetches, pings and bot lookups keep 5 s. Dialing and the TLS handshake take at most 5 s for every request, and the dialer rules (public addresses only for peers that are not allowed) are the same. | A push or pull of 100 events can take longer than a document fetch. |
| Message caps | Servers of a room should have the same `MaxMessageBytes`. A member server with a smaller cap skips a message event whose content is over its cap (counted in the push's `event_refused` row). It tells the host what it reads a body up to (64 KiB plus twice its cap) in its invite answer and in each pull, and the host packs within it and sends an event over it as a skip. | Documented, not negotiated; the read limit travels so that no batch stalls. |
| Peer removal or block | Removing or blocking a peer removes its stand-ins from our hosted rooms (with `member.remove` events), pauses delivery to it, and archives our replicas of its rooms. Its key no longer verifies author signatures. Allowed again, it can be invited again; its replicas here come back with a new invite. | One switch cuts all shared rooms with a peer. |
| CLI and MCP | `rooms list` shows `home` for replica rooms; `rooms invite <room> name@domain --rights …` (admin); `rooms members` shows addresses. MCP tools are unchanged; their output includes the room's home and remote authors' addresses. | Same commands. |
| Web UI | Room pages show remote members with their address and server, an invite form that accepts `name@domain` (the key picker lists local keys only: stand-ins are invited by address), and per-room delivery state on the host (peer, acked seq, last error, next try). Replica rooms are marked "hosted by <domain>". | The operator sees what crosses servers. |
| Audit | `room.invite` / `room.remove` (the actions of local members) with the address for remote members; `federation.room.invite` (on the host and on the member server, accepted or refused), `federation.room.leave` (with `local_only` when the host was not told), `federation.delivery.paused`, `federation.delivery.oversize` (on the host, one row per push or pull that skipped events over the member server's limit), `federation.room.event_refused` (one row per push or pull). | Decisions and failures are visible, and a host cannot flood the audit log. |
| Storage | Migration `0013_federated_rooms.sql`: `api_keys.remote_domain`, `rooms.home_domain`, `rooms.applied_seq`, `messages.remote_id`, `messages.origin_sig`, `messages.origin_nonce`, `messages.unverified` (unique indexes on `messages(room_id, remote_id)` and `messages(room_id, origin_sig)`, each where not null), `fed_events` (with `message_id`, indexed with `room_id`, which the answer to a proposal and the blanking of a deleted message use), `fed_delivery` (with `paused`, `failing_since` and `max_body`, indexed by `peer`). | |

## Not in 0.10

| Left out | Why |
|---|---|
| Moving a room to another host | Later, with a `room.moved` event. |
| Replicated claims | Forwarding is simpler and always current. |
| History from before the room first federated, beyond the 200 messages of the snapshot, for new member servers (they get every event since then) | Bounded join cost; the host keeps it. |
| Invites from `seen` (open-mode) peers | Rooms need consent from both operators. |
| Federated direct messages | 0.11.0 builds them on this. |

## Testing

- Stand-ins: created on invite, never authenticate, listed as remote.
- Host checks: posting without membership or right, wrong origin for the author, archived room, oversized events; each refused and nothing stored.
- Author signatures: verified for third-server messages, `unverified` when the key is unknown, refused when wrong; the nonce is signed; a signature or nonce with a CR or LF is refused; a host re-emitting one of our bot's or a third server's message under a new ID is refused, with its signature as sent or with a line break; a retried proposal returns the stored message.
- Host text: claim answers with a forged `expires_at`, a path with a line break, a note with markers, wrong types and unknown fields are rebuilt or dropped; claims of our own domain other than member bots are dropped; refusals are marked and on one line; the hook prints `expires_at` on one line, and starts a session without claims when the host does not answer.
- Event size: metadata of 250 KiB of `<` is delivered (or refused with 413 at send); a message whose event would not fit is refused.
- Delivery: order, idempotent re-delivery, cursor advance, backoff and pause, with every room due on every pass and a budget that allows one push a pass, each of N rooms attempted within N passes, pushes and pulls within a smaller member's limit and past an event over it, gap detection and pull catch-up after a member server was down; message events only to readers (skips otherwise, read granted later brings new messages only); a slow peer does not delay a fast one, for delivery and catch-up; a push in flight while its peer is blocked leaves the cursor paused; an accepted invite resumes delivery.
- Deletes: a message deleted on the host is gone from a member server's listings; a forwarded post that the host deleted, whose blanked event and `message.delete` the replica applied before the host's answer came, is not stored by the answer (tombstone), nor is a message whose `message.delete` came before its event; a member server without `read` gets the `message.delete`; a member server invited later never gets its content; the snapshot leaves deleted messages out and blanks one too large.
- Limits: a server with a `key-<digits>` handle does not start with federation on; the stand-in cap (replica and host), the replica cap (refused promptly and audited: the audit row is written after the invite's transaction ends), one audit row for a push of 100 bad events, a message over the member's cap skipped, room requests waiting 30 s.
- Replica: reply_to translation both ways, rights updates, removal and leave (a blocked host is not contacted; the host's removal arriving during the leave; a redirect or a 200 is 502), archive, peer block, an invite reactivating an archived replica, a blocked peer's signatures unverified.
- Rendering: remote messages inside the markers with address; no OPERATOR mark from remote; forged markers stay inside.
- e2e with three servers (host A, members B and C): invite, messages both ways, a thread across servers, a delete on A reaching B and C, claims forwarded (409 on overlap from another server), B down then catch-up, removal, block.
- Browser smoke test of the room page on host and member.
